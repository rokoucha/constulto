# constulto レビュー

ユーザーが独立したAIレビューを求めた時、または設計・実装上の未解決なリスクを別の視点から検証する必要がある時に使う。

1. 目的、成功条件、ユーザー制約、現在の提案、却下案とその理由、非目標とその理由、確認済みの事実、未検証の仮定、未解決の質問を短い依頼書にまとめる。ユーザーの決定、自分の提案、仮定を区別する。
2. まずdry-runを行い、レビュー担当、レビュー対象、アクセス可能な範囲、未追跡ファイル、対象ハッシュ、設定の出所を確認する。無関係な機微情報が見つかった場合は除外し、除外できなければ送信を止める。
3. ユーザーが送信先を指定してレビューを依頼した場合、その依頼は、対象タスクのレビューに必要な依頼書、差分、関連ソース、README、依存定義、テストなどをその送信先へ渡す許可を含む。ファイル名の列挙や具体的なペイロードへの別途承認を要求しない。同じタスク・送信先で必要な資料の追加や修正後の再レビューにも、この許可を適用する。送信先が未指定で外部サービスの利用が依頼から判断できない場合や、別リポジトリ・別目的へ範囲を広げる場合だけ、不足する許可を確認する。資格情報、無関係な機微情報、ignoredファイル、リポジトリ外のファイルの送信は、通常のレビュー依頼から許可されたと解釈しない。上位のポリシーや実行環境の承認審査には従い、拒否された場合はその理由を伝える。
4. 最初は1担当だけに依頼する。レビュー種別には `design`（設計）または `implementation`（実装）を使う。対象へ加える未追跡ファイルは明示する。正式な引数は `constulto review --help` で確認する。
5. レビュー結果は証拠であり権威ではない。重要な指摘をコード、仕様、テストと照合する。次に元の目的と実物へ戻り、レビュアーと自分の双方に欠けた前提・観点・反例がないか一度再点検する。原文をそのまま人間へ転送しない。
6. 各指摘を `accepted`（採用）、`rejected`（却下）、`needs-decision`（人間の判断が必要）、`unverified`（未検証）に分類する。実行開始時に表示された `records` 配下の `assessment.md` に、元の指摘ID、分類、理由、検証根拠を追記し、レビュアーの原文は変更しない。元のタスクが実装変更を許可している場合に限り、明白な不具合を修正する。
7. 検証済みの結論、残るトレードオフ、未確認の範囲、`stale`（対象変更により古くなった状態）を人間へ報告する。レビュアーの同意や空の指摘一覧を正しさの証明にしない。

正式なコマンド仕様はCLIのhelpを原本とする。アダプターのフラグを推測したり、読み取り専用の制限を緩めたりしない。合意するまでレビューを繰り返さず、追加レビューは具体的な未解決事項と新しい根拠がある場合だけ行う。
